# 接片室 vlog-stitch

在手機瀏覽器裡把當天拍的照片和影片剪成一支 vlog：自動排順序、寫字幕草稿，加上照片動態、轉場和配樂，匯出成可以直接上傳 YouTube 的檔案。字幕會先列出來讓你逐句確認，你按下確認之後才開始轉檔。

只想把幾段影片原封不動接起來也可以，那是它原本的用途，做法沒有變。

單一個 `index.html`，沒有後端、沒有建置流程、沒有 npm 安裝。照片、影片和聲音全程留在手機裡，不會上傳到任何伺服器。唯一的例外是你自己開啟的「AI 看圖寫字幕」，那時縮小過的畫面會直接傳給你選的那一家 AI（Gemini、Azure Foundry 或 Anthropic），細節寫在[限制](#幾個一定要知道的限制)裡。

---

## 怎麼開始用

**方式一：GitHub Pages（推薦，手機最方便）**

1. 這個 repo → Settings → Pages → Source 選 `Deploy from a branch`，分支選 `main`、資料夾選 `/ (root)`
2. 等一兩分鐘，會得到 `https://<你的帳號>.github.io/vlog-stitch/`
3. 手機用 Chrome 開這個網址，加到主畫面就跟 App 一樣

需要 HTTPS 的功能（螢幕恆亮、WebGPU 加速）在 Pages 上才會生效，所以不建議直接用 `file://` 開。

**方式二：本機起一個伺服器**

```bash
python3 -m http.server 8080
# 瀏覽器開 http://localhost:8080
```

## 支援環境

| 環境 | 合併／匯出 | 自動字幕 |
|---|---|---|
| Android Chrome | 可 | 可（建議 Wi-Fi） |
| 桌機 Chrome / Edge | 可 | 可 |
| iOS Safari 17+ | 大致可 | 記憶體吃緊，容易失敗 |
| Firefox | 匯出為 webm | 需開啟 Worker 模組設定 |

照片、效果、配樂、字幕草稿與字幕確認是 v10 加進來的。這一批功能目前只在桌機的 Chromium 上用自動化測試跑過（見[測試](#測試)），手機上還沒有實機驗證。

## 功能

**快速成片**　照片變 vlog 最短的路：

1. 在「素材」頁選今天拍的照片和影片，可以混著選
2. 按「產生草稿，確認字幕」。它會依拍攝時間排好順序，替每一段寫一句字幕草稿，套上照片動態、交叉淡化、模糊填滿和內建配樂
3. 字幕確認畫面會把每一句連同那一刻的畫面列出來，逐句看過、改好，按「確認，開始轉檔」
4. 下載或分享成品

每一步也都可以自己來，下面是各分頁能做的事。

**素材**
- 一次選多張照片、多段影片，上下箭頭排順序，或一鍵依拍攝時間排序（照片讀 EXIF，影片用檔案時間）
- 照片預設每張 3 秒，可以整批改成 2～5 秒，也可以單張調 1～10 秒；帶旋轉資訊的照片會自動轉正
- 影片每段可以獨立裁掉頭尾（拖滑桿，或播到某個點按「目前位置設為起點」）
- 比例不一樣的素材可以選「留黑邊」「裁切填滿」或「模糊填滿」（用同一張畫面的模糊版墊在後面）
- 輸出 720p / 1080p，直式或橫式，幀率可壓到 30fps（60fps 素材的編碼量直接減半）

**字幕**
- 字幕草稿：替每一張照片、每一段影片先寫一句。兩種寫法可以切換：
  - 離線：不連網，照拍攝時間寫出日期和時段（例如「11月14日 週六」「中午 12:31」），當成等你改寫的底稿
  - AI 看圖：把縮小的畫面傳給 AI，照畫面內容寫。供應商三選一，填你自己的金鑰：Gemini（預設）、Azure Foundry（OpenAI 相容的模型部署）或 Anthropic
- 自動聽打：影片裡有人講話時用。Whisper 模型直接在瀏覽器跑，支援中／英／日，跑在背景執行緒不卡畫面，可隨時停止
- **轉檔前一定先確認**：字幕只要在上次確認之後動過（自動產生、聽打、匯入、手改都算），按下匯出就會先停在確認畫面，你按下確認才開始轉檔
- 草稿和聽打的字幕會跟著素材走：素材換順序、改秒數、重新裁切，字幕的時間會自動重算
- 字幕列表可以逐句改字、改時間，全選、勾選刪除、清空
- 五種樣式：經典、綜藝、底條、細字、大字卡；位置上中下、大小 60%–180%
- 可以匯入／匯出 SRT，跟其他工具接得起來

**效果與配樂**
- 照片動態：推近、拉遠、平移，或讓它每張輪流換
- 轉場：交叉淡化、淡入淡出、滑動、放大淡出。有開轉場時，整支影片的片頭片尾也會淡入淡出
- 色調：暖色、冷調、黑白、底片
- 配樂：三首內建配樂（輕快、溫暖、放鬆），或選自己的音樂檔。比影片短會自動循環，片頭淡入、片尾淡出，影片有原音的段落自動壓低
- 配樂和影片原音的音量可以分開調

加入照片時會自動套上一組預設（照片動態、交叉淡化、模糊填滿、內建配樂），你自己調過的項目不會被覆蓋。只有影片的時候什麼都不會自動開。

**匯出**　三種方式，在匯出頁自己選：

| 方式 | 速度 | 字幕 | 用在什麼時候 |
|---|---|---|---|
| 快速接片 | 幾秒 | 另存 SRT | 只有影片，而且片段編碼、解析度都一樣時的最佳選擇，畫質零損失 |
| 重新編碼 | 比即時快數倍 | 燒進畫面 | 有照片、要硬字幕、要效果和配樂，或素材規格不一致 |
| 即時錄製 | 跟影片一樣長 | 燒進畫面 | 瀏覽器沒有 WebCodecs 時的相容退路 |

- 輸出 mp4，可以直接上傳 YouTube
- 手機支援的話可以直接用系統「分享」丟進 YouTube App
- 有可以連線的話會寫進 OPFS 檔案而不是記憶體，長片才不會爆掉
- 匯出頁有**診斷記錄**，逐段列出編碼、解析度、可否解碼、封包數與出錯位置，可複製或存檔

## 幾個一定要知道的限制

**照片、效果和配樂都要重新編碼。** 快速接片完全不碰畫素和聲音，所以沒辦法把照片變成影片，也加不了轉場、色調和配樂。素材裡有照片時會自動改用重新編碼並說明原因。只有影片、選了快速接片、又開了效果的時候，它會照你選的快速接完，效果不套用，完成訊息和效果頁都會提醒。

**離線草稿只知道拍攝時間。** 不連網就看不懂畫面，所以離線草稿寫的是日期和時段，內容要自己改。想要照畫面寫，就用 AI 看圖。

**AI 看圖寫字幕會把畫面傳出去。** 這是整個工具唯一會把素材送出裝置的功能，而且要你自己選了「AI 看圖寫」、填了金鑰才會動：
- 每張照片先縮成最長邊 768 像素的 JPEG，影片只取一格畫面，原始檔不會傳。請求從你的瀏覽器直接送到你選的那一家，中間沒有其他伺服器。
- 用的是你自己的金鑰和額度。一次請求最多送 20 張，超過會分批。
- 金鑰預設只留在這一頁的記憶體，關掉分頁就沒了。勾選「記在這台裝置」才會存進瀏覽器的 localStorage，共用的裝置不要勾。三家的金鑰各存各的，切換供應商不會互相蓋掉。

三家要填的東西不一樣：

| 供應商 | 要填什麼 | 畫面送到哪裡 |
|---|---|---|
| Gemini（預設） | Google AI Studio 的 API key、模型名稱（預設 `gemini-3.8-flash`，可以自己改，或按「查可用模型」列出這把金鑰能用的） | `generativelanguage.googleapis.com` |
| Azure Foundry | 資源端點、API 金鑰、部署名稱 | 你填的端點，走 OpenAI 相容的 `/openai/v1/chat/completions` |
| Anthropic | API key、模型（預設 Claude Opus 5.5，可改 Sonnet 5.5 或 Haiku 5.5） | `api.anthropic.com` |

- **Azure Foundry 的「部署名稱」是你在 Foundry 上替模型取的名字，不是模型本身的名稱**，而且要是能看圖、支援結構化輸出的對話模型。端點可以直接貼 Foundry 給的網址（資源端點、專案端點、已經帶 `/openai/v1` 的都可以），程式會自己整理。
- Anthropic：組織開了零資料保留（ZDR）時，API 不接受從瀏覽器直接呼叫，會回 401。Opus 和 Sonnet 的請求帶了伺服器端的拒絕備援（`fallbacks`），被安全分類器擋下時會自動換模型重跑。Claude 一張圖的輸入量大約是 ⌈寬÷28⌉×⌈高÷28⌉ 個 token，768×576 的畫面約 588 個。
- 出錯時會把原因講清楚：金鑰不對、找不到模型或部署、額度用完（會附上供應商自己的說明）、被內容篩選擋下，都不會當成空字幕默默吞掉。

**AI 寫的字幕也只是草稿。** 模型看得到畫面，看不到你當下在想什麼，也可能看錯。所以不管草稿是哪一種寫法，轉檔前都會先停在確認畫面。

**內建配樂是算出來的。** 三首內建配樂是程式當場合成的八小節循環，沒有帶任何音檔，所以沒有版權問題，但聽起來也比較陽春。要好聽就選自己的音樂；要上傳到平台的話，音樂的授權要自己確認。

**有些照片瀏覽器打不開。** iPhone 的 HEIC 照片在 Android 的 Chrome 上解不開，會在素材列表標示出來，先轉成 JPEG 再選。有讀不到的素材時不會開始轉檔。

**預覽是即時播的。** 預覽和即時錄製模式靠 `<video>` 元素和 Web Audio 即時播放，轉場與配樂的時間點可能跟成品差一點。重新編碼的成品是逐格算的，以成品為準。

**快速接片有前提。** 所有片段的影像編碼、解析度、編碼參數必須一致，聲音的編碼、取樣率、聲道數也要一致。同一支手機用同一個 App 拍的通常沒問題，混到不同來源就不行。不符合時會自動改用重新編碼，並在畫面上說明原因。

**快速接片的裁切點會對齊關鍵影格。** 因為完全沒有重新編碼，只能從關鍵影格開始切，實際起點可能比你設定的早一兩秒。匯出後會告訴你有幾段被移動過。需要精準裁切就用重新編碼模式。

**重新編碼模式不會碰聲音解碼器。** 影像非重編不可，但聲音只要各段規格一致就直接複製原始封包（`EncodedAudioPacketSource`），完全繞過解碼器，也沒有二次壓縮。實測 Android 上這台裝置的 AAC 解碼器建不起來，靠這條路才留得住聲音。規格不一致時才退回解碼重編。加了配樂、素材裡有照片，或調過原音音量的時候，聲音一定要解碼才能混在一起，就走不了這條路。

**聲音解碼有可能失敗。** 實測在 Android 上遇過 `canDecode()` 回報 true、但 WebCodecs 的 `AudioDecoder` 建立時仍丟 `EncodingError: Decoding error.`。重新編碼模式因此採三層退路：WebCodecs → Web Audio 的 `decodeAudioData` → 等長靜音。任何一層成功就繼續，不會讓整趟匯出白跑，實際走到哪一層記錄裡都寫得清楚。

**素材必須真的在手機本機。** 從 Google 相簿、OneDrive 之類的雲端相簿選檔案時，拿到的可能只是佔位參照，讀取時會丟 `TypeError: network error`。開檔前會先試讀開頭幾十 KB，讀不到就直接指名是哪一段，不會跑到一半才失敗。

**記憶體不是瓶頸，儲存空間才是。** 讀取端是串流的，不會把素材載進記憶體；成品也直接寫進 OPFS。真正的上限是瀏覽器給的磁碟配額（實測 Android 上約 10GB）。匯出前會估算成品大小並跟可用空間比對，不夠就先擋下來。

**手機不一定解得開 HEVC。** 不少 Android 手機預設用 H.265 錄影，但 Chrome 的 WebCodecs 對 HEVC 支援看裝置。重新編碼模式開始前會先用 `canDecode()` 檢查，解不開會直接擋下並指出是哪一段，不會跑到一半才失敗。快速接片不需要解碼，所以不受影響。

**只有即時錄製模式會跑滿影片長度。** 那是 MediaRecorder 錄 canvas 的舊做法，留著當退路。匯出中都不要切到別的 App。

**自動聽打很吃資源。** 第一次要下載模型（tiny 約 40MB、base 約 80MB、small 約 250MB）。辨識跑在 Web Worker 裡，過程中畫面照樣能操作，也可以隨時按停止。素材很長的話建議先用 tiny 試。

## 程式架構

全部在 `index.html` 裡，分成幾塊獨立的模組物件：

```
state              單一狀態物件：clips[]、subs[]、樣式、效果與輸出設定
├─ photo           照片：解碼、轉正、縮圖、讀 EXIF 拍攝時間、匯出用的工作圖
├─ clips           素材管理：照片與影片的加入、探測 metadata、排序、裁切、秒數
├─ subs            字幕資料：新增、勾選、刪除、SRT 匯入匯出、跟著素材重算時間
├─ draft / ai      字幕草稿：離線照拍攝時間寫，或用 AI 看圖寫（Gemini／Azure Foundry／Anthropic）
├─ fx              畫面效果：照片動態、轉場、色調、模糊填滿
├─ synth / bgm     內建配樂的合成、配樂的音量曲線與混音
├─ engine          即時預覽與 MediaRecorder 退路
├─ asr             Whisper 自動聽打
├─ dbg             診斷記錄，出問題時唯一能看的東西
├─ mb / xport      WebCodecs 匯出引擎（核心，用 mediabunny）
├─ review / quick  字幕確認（轉檔前的最後一關）、快速成片
└─ ui              所有畫面渲染與事件
```

**照片怎麼變成影片**

照片在片段列表裡跟影片是同一種東西，只是 `kind:'photo'`、長度是你設定的秒數。重新編碼時 `xport.photoFrames()` 用固定幀率一格一格畫進 canvas，照片動態就是每一格的縮放和位移不一樣。原圖動輒上千萬畫素，逐格縮放會很慢，所以 `photo.work()` 先把它縮到「剛好夠輸出尺寸再加一點推近空間」，同時最多留三張在記憶體裡。

預覽和匯出畫每一格都走同一套：`fx.paint()` 畫底圖（留黑邊／裁切填滿／模糊填滿），`fx.finish()` 依序套色調、轉場、片頭片尾淡入淡出，最後才疊字幕，所以轉場時字幕不會跟著糊掉。色調用 canvas 的混合模式做，不用 `ctx.filter`，Safari 也能跑。

**轉場不需要同時解碼兩段**

匯出引擎是一段一段依序處理的，沒辦法同時拿到前後兩段的畫面。所以每段快結束時把畫面留一份在離屏 canvas（凍結的最後一格），下一段開頭再把它疊上去慢慢淡出、滑走或放大。這樣成品長度不會變，聲音也完全不受影響。「淡入淡出」連留存都不用，各自在段尾、段頭蓋一層黑就好。

**聲音的四種處理方式**

`xport.audioPlan()` 依素材和設定挑一種，記錄裡會寫清楚用了哪一種：

| 方式 | 什麼時候 | 做法 |
|---|---|---|
| none | 沒有原音也沒有配樂 | 成品沒有聲音軌 |
| copy | 全是影片、聲音規格一致、沒有配樂 | 直接搬原始封包，不碰解碼器 |
| decode | 全是影片、聲音規格不一致、沒有配樂 | 解碼後重編 |
| mix | 有配樂、有照片，或調過原音音量 | 解碼後跟配樂混在一起再編碼 |

混音由 `makeMixer()` 負責。它記著已經送出幾個樣本，那個數字就是聲音在成品時間軸上的位置。每一塊解碼出來的原音都照**它自己的時間戳**擺位置，而不是一塊接一塊往後排，音軌中間有缺口或解碼器多吐少吐一點，都不會讓後面整段偏掉；每段結束時再補齊或截斷到剛好等於那一段影像的長度。照片沒有原音，那一段就是靜音加配樂。取樣率跟成品不同的片段用 `makeResampler()` 逐塊換取樣率，它會把上一塊的最後一個樣本和小數位置留到下一塊，接縫才不會有喀聲。

配樂的音量由 `bgm.gainAt(t)` 一個函式決定：片頭淡入、片尾淡出、有原音的區段壓低，預覽和匯出用的是同一條曲線。內建配樂由 `synth.render()` 直接算出波形，音符的尾巴超過結尾時會繞回開頭，所以循環起來沒有接縫。

**字幕跟著素材走**

字幕的 `start`／`end` 一直都是成品時間軸上的秒數。草稿和聽打產生的字幕另外記著它屬於哪一段素材，以及它在那段素材裡的位置（照片草稿是整張照片、影片草稿是開頭幾秒、聽打字幕是原始影片裡的時間）。素材換順序、改秒數、被裁切或移除之後，`subs.relink()` 重新算出成品上的時間；落在裁切範圍外的字幕會標示出來，不會出現在成品裡。手動新增和匯入 SRT 的字幕沒有這層關係，時間固定不動。

**字幕確認怎麼擋下轉檔**

`state.subsOk` 記著字幕在上次確認之後有沒有變動，所有會改到字幕內容的地方都經過 `subs.touch()` 把它設回未確認。匯出按鈕走的是 `ui.exportClick()`：字幕還沒確認就打開確認畫面（`review`），使用者按下確認才呼叫真正開工的 `xport.run()`。`xport.run()` 本身不管確認這件事，測試才能直接驅動它。

**AI 看圖寫字幕**

三家供應商共用同一套流程，只有「怎麼包請求、怎麼拆回應」不一樣：

- 共用的部分：`ai.image()` 把每段素材縮成一張 JPEG；`ai.prompt()` 把編號、類型、拍攝時間和圖片排成一串文字與圖片交錯的內容；`ai.captions()` 每 20 張分一批，後面的批次會帶著前面已經寫好的字幕，語氣才接得上；`ai.pick()` 把模型回的 JSON 拆成 `{編號: 字幕}`。
- 三家都用結構化輸出要回同一個形狀 `{captions:[{index,text}]}`，不用自己從文字裡撈。
- Gemini：直接 `fetch` 原生的 `generateContent`，金鑰放在 `x-goog-api-key` 標頭，系統提示放 `system_instruction`，圖片用 `inline_data`，格式用 `generationConfig.responseSchema`。
- Azure Foundry：直接 `fetch` OpenAI 相容的 `/openai/v1/chat/completions`，金鑰放在 `api-key` 標頭，`model` 填部署名稱，圖片用 data URL 的 `image_url`，格式用 `response_format` 的嚴格 JSON schema。
- Anthropic：用官方的 `@anthropic-ai/sdk`，從 CDN 動態載入，以 `dangerouslyAllowBrowser` 讓瀏覽器直接呼叫，格式用 `output_config.format`。

模型拒絕、被內容篩選擋下或回覆被截斷時直接報錯，不會當成空字幕默默吞掉。

**xport：兩條快速路徑**

兩條都建立在 [mediabunny](https://mediabunny.dev) 上，它把 WebCodecs 包成好用的 API，並補上 WebCodecs 沒有的 mux／demux。從 CDN 動態 `import()`，不進版本庫。

*快速接片（`xport.remux`）*　完全不碰畫素。用 `EncodedPacketSink` 把每段的封包讀出來，`packet.clone({timestamp})` 位移時間戳，再用 `EncodedVideoPacketSource` / `EncodedAudioPacketSource` 寫進同一個 mp4。第一個封包要附上 `decoderConfig`，後面就不用。裁切用 `getKeyPacket(trimStart)` 找關鍵影格起點，所以會有對齊誤差。開跑前先用 `checkCompat()` 比對所有片段的編碼參數，包含 `description` 的位元組，不一致就擋下來改走重新編碼。

*重新編碼（`xport.encode`）*　**每段先處理聲音再處理影像**。聲音便宜又最容易失敗，先跑才能在花好幾秒編完影像之前就知道出事。影像用 `VideoSampleSink.samples(start, end)` 逐格取出解碼後的畫面，`drawWithFit()` 依「留黑邊／裁切填滿」畫進 canvas，疊上該時間點的字幕，再交給 `CanvasSource.add(timestamp, duration)` 硬體編碼。聲音走 `AudioSampleSink` → `toAudioBuffer()` → `AudioBufferSource.add()`；`AudioBufferSource` 會把每個 buffer 依序接在前一個後面，所以不用自己算時間戳。**沒有聲音軌的片段會補一段等長靜音**，否則後面所有片段的聲音都會提前，畫面對不上嘴。

**匯出前的預檢**

`xport.preflight()` 在動工前先把每段的規格全部寫進診斷記錄：編碼字串、coded 尺寸、旋轉、fps、`description` 長度、聲音參數，以及最重要的 `canDecode()`。重新編碼模式下只要有一段解不開就直接擋下，訊息會指名是第幾段、什麼編碼，不會跑到一半才丟一句 `Decoding error`。

**位元組比對的坑**

`decoderConfig.description` 是 TypedArray 視圖，直接讀 `.buffer` 會拿到整個底層緩衝區（實測是幾萬位元組，而 hvcC 其實只有幾百）。這會讓相容性判斷永遠誤判成「參數不同」，把本來可以秒出的素材推去重新編碼。`toBytes()` 用 `byteOffset` / `byteLength` 取出真正的內容，記錄裡也會印出長度和開頭幾個位元組方便核對。

**輸出目的地**

預設寫進 OPFS（`navigator.storage.getDirectory()` → `createWritable()` → mediabunny 的 `StreamTarget`），完成後用 `getFileHandle().getFile()` 取回。這樣成品不會整個堆在 JS heap 裡——43 分鐘的 1080p 光是緩衝就好幾 GB，手機一定撐不住。環境不支援時才退回 `BufferTarget`，記錄裡會註明用的是哪一種。

**engine 的運作方式（即時錄製退路）**

1. `outSize()` 依素材方向和設定算出輸出畫布尺寸
2. 開始前先把每段影片都 seek 到各自的起點，減少接點空白
3. 建立 `AudioContext`：每段影片一個 `MediaElementSource`，先過 `orig`（原音音量），再同時接到
   - `recDest`（`MediaStreamDestination`，錄進成品）
   - `monitor`（GainNode → 喇叭，可靜音）

   配樂是一個循環播放的 `AudioBufferSourceNode`，音量照 `bgm.gainAt()` 的曲線排程，一樣接到這兩個出口
4. `canvas.captureStream(30)` 拿視訊軌，加上 `recDest` 的音訊軌，餵給 `MediaRecorder`
5. 依序播放每段，`requestAnimationFrame` 逐格把畫面畫進 canvas，同時查當下時間該顯示哪句字幕、直接畫上去（燒錄字幕）。照片沒有東西可以播，就照時鐘算它播到第幾秒
6. 影片播到 `trimEnd`、照片播滿秒數就換下一段，全部跑完停止錄製，組成 Blob

字幕時間軸是**成品的時間軸**（全域），不是各段自己的時間。`clipOffset(i)` 負責換算。

**字幕繪製**

`tokenize()` 把中文拆成單字、英文拆成單詞，`wrapLines()` 再貪婪塞行，所以中英夾雜也能正確斷行。`drawSubtitle()` 依樣式畫描邊、底條或陰影，字級是畫布高度的比例，不同解析度看起來一樣大。

**自動聽打**

推論跑在 Web Worker 裡，主執行緒不會被佔住。Worker 的原始碼放在 `<script id="asrWorkerSrc" type="text/worker">` 區塊，瀏覽器不會執行它；主程式讀 `textContent` 包成 Blob URL，再用 `new Worker(url, {type:'module'})` 啟動，所以整包還是維持單一檔案。

分工是這樣：

- **主執行緒**負責取聲音。`asr.pcm()` 用 `decodeAudioData` 解碼，再用 `OfflineAudioContext` 重採樣成 16kHz 單聲道（Whisper 要求的格式），只取裁切範圍那一段。`AudioContext` 在 Worker 裡拿不到，所以這步必須留在主執行緒。
- **Worker** 負責推論。模型從 CDN 動態 `import()` 進來，有 WebGPU 就用 WebGPU，沒有就退回 WASM，載入一次之後所有片段共用。

兩邊用 `{id, type, payload}` 訊息溝通，`asr.jobs` 這個 Map 依 id 對應回各自的 Promise。PCM 用 transferable 傳過去（`postMessage(msg, [pcm.buffer])`），不會複製一份。

按停止就直接 `terminate()` 掉 Worker，當場中斷，這是搬進 Worker 之後才做得到的事。如果瀏覽器不支援 module worker（例如沒開設定的 Firefox），會自動退回主執行緒模式，只是畫面會頓、停止要等當前片段跑完。

## 測試

`test/` 底下有兩套測試，測的都是會上線的那份 `index.html`，細節見 `test/README.md`。

**匯出引擎**　直接從 `index.html` 抽出主程式，接上 Node 版 mediabunny，用**真的影片和照片**跑完整匯出，再用 ffmpeg 把成品拆開來量。

```bash
cd test && npm install && ./run.sh
```

測試影片的三段各用 300／600／900Hz 的音調，測試照片是三張純色圖，所以接續順序、音畫同步、轉場、色調和配樂混音都可以直接用頻率和顏色驗證。

**操作流程**　用 Playwright 開真的 Chromium，把「選檔 → 快速成片 → 確認字幕 → 轉檔」整個走一遍，包含字幕確認有沒有確實擋下轉檔。

```bash
cd test && npm install playwright && npx playwright install chromium
node browser.js
```

AI 看圖寫字幕的三家供應商，平常是攔下請求檢查內容、再回假的回應。有設 `GEMINI_API_KEY`，或 `AZURE_OPENAI_ENDPOINT`＋`AZURE_AI_KEY`（＋`AZURE_CHAT_DEPLOYMENT`）這些環境變數時，最後會再用真的金鑰實測一次，會用到一點額度。
